S3-Backed Object and Reference Stores
=====================================

Overview
--------

Problem statement
~~~~~~~~~~~~~~~~~

Hosting Git on traditional filesystems forces every server that participates in
serving a repository to mount that repository's working storage. Scaling such a
deployment requires either replicating the data, sharing it via a network
filesystem, or routing every request to a small number of "owning" nodes. Each
of these is operationally expensive and limits how Git fits into modern
cloud-native infrastructure.

Cloud object storage (Amazon S3 and S3-compatible services such as SeaweedFS)
offers a different model: a durable, highly available shared namespace
addressed over HTTP, with no notion of a mounted volume. Pushing Git's
persistent state into such a service lets any number of stateless machines
serve the same repository, paying only the cost of a small local cache.

Goals
~~~~~

* Persist objects and references to an S3-compatible bucket so that the
  authoritative state of a repository can be shared between many machines
  without a shared filesystem.

* Provide a consistent, point-in-time view of refs and objects together. A
  reader who pins to a particular state must see refs that resolve only to
  objects which were already present in that state.

* Keep the local working set small. Machines should cache only what they
  actually consult; the bulk of the repository may remain in object storage.

* Work uniformly against both Amazon S3 and other implementations of the S3
  protocol (e.g. SeaweedFS).

Non-goals
~~~~~~~~~

* This backend is not a promisor remote and does not implement partial-clone
  semantics. All objects referenced by the manifest must be retrievable.

* The current iteration assumes single-writer-at-a-time semantics. Detecting
  and resolving concurrent writers via compare-and-swap on the manifest pointer
  is future work; see <<future-work>>.

* Workloads dominated by large numbers of cold random reads are not the primary
  target. The design optimises for repositories that are read in bulk and
  updated periodically.

Architecture at a glance
------------------------

The backend has two pluggable extension points that share the same underlying
S3 client:

* The object database extension (`extensions.objectStorage`) installs an ODB
  source that fetches packfiles from S3 and serves reads from a local pack
  cache.

* The reference storage extension (`extensions.refStorage = s3`) installs a
  ref backend that wraps the existing reftable backend.  Its job is to keep
  the reftable directory in sync with object storage; all actual reftable
  reads and writes go through the wrapped backend.

Both extensions cooperate through a single shared object: the S3 storage
handle, which is reference-counted and deduplicated by URL.  When the ODB
source and the ref backend point at the same bucket and prefix, they obtain
the same handle and therefore share a single in-memory view of the manifest
(see <<manifest-cache>>).

----
+--------------------+      +-----------------------+
| S3 object source   |      | S3 reference backend  |
| - fetches packs    |      | - fetches reftables   |
| - writes packs     |      | - writes reftables    |
+----------+---------+      +-----------+-----------+
           \                            /
            \                          /
             v                        v
           +-------------------------------+
           | Shared S3 storage handle      |
           | - Manifest handling           |
           | - Endpoint configuration      |
           | - Credentials                 |
           +---------------+---------------+
                           |
                           v
                  +-----------------+
                  | S3-compatible   |
                  | bucket          |
                  +-----------------+
----

[[layout]]
Storage layout in S3
--------------------

A repository is identified by an `s3://` URL of the form

----
s3://<endpoint>/<bucket>/<prefix>
----

where `<endpoint>` is the HTTP authority of the S3 service, `<bucket>` is the
bucket name, and `<prefix>` is the key prefix that scopes a single repository
within the bucket.

Within such a `<prefix>` the layout is:

----
<prefix>/manifest                  mutable pointer to the current manifest
<prefix>/manifests/<sha256-hex>    immutable, content-addressed manifest versions
<prefix>/packs/<hash>.pack         immutable packfiles
<prefix>/packs/<hash>.idx          immutable pack indexes
<prefix>/packs/<hash>.rev          immutable pack reverse indexes
<prefix>/reftable/<table-name>     immutable reftable files
----

Every object except `<prefix>/manifest` is content-addressable and immutable.
The single mutable pointer at `<prefix>/manifest` contains the hash of the
manifest version that constitutes the current authoritative state of the
repository.

A manifest is a small text file enumerating the active artifacts.  Lines
beginning with `p:` list packfiles by their bare hex hash; lines beginning with
`r:` list reftables by their on-disk file name:

----
p: 3472ebb5128456d753dee031162e0a4daef8e0bd
p: 86a2525d853315ebbeb6d3521c582b6cbc461783
r: 0x000000000001-0x000000000002-c35103bc.ref
r: 0x000000000003-0x000000000003-57856642.ref
----

Combining packs and reftables into a single manifest is deliberate: a single
pointer flip atomically advances both the object database and the reference
store, which is what makes consistent snapshot reads across both subsystems
possible (see <<concurrency>>).

Local cache layout
------------------

Each machine maintains a small mirror of the artifacts it has actually used.
The local layout is:

----
<commondir>/s3-cache/manifests/    downloaded manifest versions
<commondir>/s3-cache/packs/        downloaded packs / indexes / reverse indexes
<gitdir>/reftable/                 mirror of reftables active in this
                                   repository
<gitdir>/reftable/tables.list.<pid>  per-process active list (see
                                   <<concurrency>>)
----

The pack cache is sized only by what the local machine has needed; it is not a
full mirror of `<prefix>/packs/`.  Reftable files are kept under
`<gitdir>/reftable/` so that the wrapped reftable backend can use them
directly, unmodified.

[[manifest-cache]]
Manifest lifecycle and in-memory cache
--------------------------------------

The manifest is fetched lazily, cached in memory for the lifetime of the
process, and updated in place whenever the process writes a new manifest
version to S3. Both the ODB source and the ref backend obtain the cache through
the shared storage handle, so they always observe the same manifest:

----
   +---------------+   first read   +-------------+
   | uninitialized |--------------->|  resolved   |<--+
   +---------------+                +------+------+   |
                                           |          | successful
                                           | write    | write
                                           v          |
                                    +-------------+   |
                                    |   updated   |---+
                                    +-------------+
----

* On first read the storage handle resolves the manifest.  If `GIT_S3_MANIFEST`
  is set, its value is taken as the desired version; otherwise the currently
  active manifest version is fetched via the manifest pointer stored in S3. The
  named version is downloaded if not already present in the local cache.

* On every successful write the handle replaces its cached snapshot with the
  manifest that was just persisted. Subsequent reads inside the same process
  observe that updated state immediately.

Read path
---------

----
+----------------+
| ODB / refs op  |
+----------------+
        |
  manifest cache hit? -- no --> +--------------------+      +------------+
        |                       | resolve manifest   |----->|     S3     |
       yes                      | (pointer + version)|<-----|            |
        | <-------------------  +--------------------+      +------------+
        |
        v
+--------------------+      +------------+
| download missing   |----->|     S3     |
| packs / reftables  |<-----|            |
+--------+-----------+      +------------+
        |
        v
+-------------------------+
| serve from local files  |
+-------------------------+
----

ODB
~~~

When the ODB source prepares it asks the storage handle for the current
manifest, walks its pack list, and downloads any pack, index, or reverse index
that is not already in the local pack cache. Each pack is then registered with
an embedded packed-object source. All subsequent object lookups go through that
local store; no further S3 traffic is incurred for reads of objects that are
already covered by the cached packs.

Reprepare requests (driven by `OBJECT_INFO_SECOND_READ`) cause the source to
discard its initialization flag so that the next access re-resolves the
manifest and absorbs any newly visible packs.

References
~~~~~~~~~~

The reference backend resolves the manifest on first use, downloads any
reftables that are not yet present locally, and writes the active list of
reftable file names to a per-process `tables.list.<pid>` (see <<concurrency>>).
All actual reference reads then go through the wrapped reftable backend, which
is unaware of S3.

Write path
----------

----
+------------------+
| build object/ref | pack file, reftable, ...
+---------+--------+
          |
          v
+--------------------+      +------------+
| upload object/ref  |----->|     S3     |
+---------+----------+      +------------+
          |
          v
+-----------------+
| update manifest |
+---------+-------+
          |
          v
+--------------------+      +------------+
| upload manifest    |----->|     S3     |
+---------+----------+      +------------+
          |
          v
+--------------------+      +------------+
| advance pointer    |----->|     S3     |
+---------+----------+      +------------+
          |
          v
+--------------------+
| update local cache |
+--------------------+
----

Object writes
~~~~~~~~~~~~~

Object writes proceed by packing the new objects into a pack, uploading the
pack, index, and reverse index to S3, then updating the manifest. The pack is
also registered with the embedded packed source so subsequent reads in the same
process see it without re-resolving the manifest.

The ODB source supports an explicit transaction interface that buffers pending
objects and flushes them as a single pack on commit. This collapses multiple
object writes into one S3 round-trip on the upload side and one manifest
update.

Packs are optimized using incremental geometric repacking. When the collection
of remote packs no longer forms a geometric progression in object count, the
smallest packs are merged into a single replacement pack which is uploaded, and
a new manifest is published in which the merged source packs are dropped and
the replacement is added.

The merge currently uses verbatim copies of pack contents: it does not
recompute deltas or detect duplicates of the same object. This strategy needs
to be adapted eventually, see <<future-work>>.

Reference writes
~~~~~~~~~~~~~~~~

Reference writes are first executed by the wrapped reftable backend, which
produces one or more new reftable files locally. When the wrapper observes the
local reftable list change, it uploads the new files and writes a new manifest.
Manifest update ordering is identical to object writes: artifacts first, then a
new manifest version, then the pointer.

[[concurrency]]
Concurrency model
-----------------

Single-writer assumption
~~~~~~~~~~~~~~~~~~~~~~~~

The current backend assumes that at most one process is writing to a given
prefix at a time. All artifacts apart from the manifest pointer are
content-addressable and immutable, so concurrent writers never collide on
artifact uploads themselves. The only contended object is the pointer at
`<prefix>/manifest`.

The pointer is updated with an unconditional PUT. Two writers that race can
therefore lose updates: each reads the same pointer value, builds a new
manifest, and writes it; whichever PUT lands second wins and the other writer's
additions vanish from the visible state. Resolving this requires
compare-and-swap on the pointer; see <<future-work>>.

Snapshot reads via content addressing
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Because every manifest version is named by the SHA-256 of its content, a reader
that has noted the current pointer value can read the named version
indefinitely without seeing concurrent writes. Combined with `GIT_S3_MANIFEST`
(see <<manifest-cache>>) this gives readers stable point-in-time snapshots that
span both refs and objects.

Tradeoffs and design decisions
------------------------------

* *Packfiles only; no loose objects.* Storing each loose object as its own S3
  key would put a request on the critical path of every object read or write.
  Packfiles amortize the cost across many objects.

* *One combined manifest for packs and reftables.* The pointer is a single
  point of mutability for the entire repository; advancing it advances refs and
  objects together. This is what makes consistent point-in-time reads across
  both subsystems possible.

* *Content-addressable manifest versions plus a mutable pointer.* Versions can
  be cached forever, replicated freely, and referenced by hash. The
  multi-writer concurrency problem is reduced to a single-pointer update, which
  can be made safe with conditional writes.

* *Eager prepare downloads all referenced packs.* Pack lookups need random
  access to the index, so streaming packs from S3 per-read would multiply
  request latencies. Downloading the full set on prepare keeps subsequent reads
  cheap; geometric repacking limits the size of that set.

* *Local cache always on, under `<commondir>/s3-cache/`.* The cache is required
  by the design rather than an opportunistic optimisation: pack index access is
  random, and re-fetching packs from S3 between accesses would be unworkable.

* *Refcounted shared storage handle.* Both the ODB source and the ref backend
  target the same bucket; sharing the handle (and its cached manifest) is what
  keeps their views consistent within a process.

Configuration reference
-----------------------

* `extensions.objectStorage = s3://<endpoint>/<bucket>/<prefix>` selects the
  S3-backed ODB source.  See `linkgit:gitrepository-layout[5]` and
  `repository-version.adoc` for general background on extensions.

* `extensions.refStorage = s3` plus a payload of the form
  `s3://<endpoint>/<bucket>/<prefix>` (passed via `GIT_REFERENCE_BACKEND` at
  init time) selects the S3-backed reference backend.  See `reftable.adoc`
  for the underlying reftable design.

* `GIT_S3_MANIFEST=<sha256-hex>` pins the process to a specific manifest
  version, giving stable point-in-time reads across both refs and objects.

* `S3_KEY_ID` and `S3_KEY_SECRET` carry the access credentials used by the
  underlying S3 client.

[[future-work]]
Future work
-----------

The current backend is functional but deliberately leaves several
improvements for later iterations:

* *Compare-and-swap on the manifest pointer.* The mutable manifest pointer is
  currently advanced by an unconditional PUT, which allows concurrent writers
  to lose each other's updates.  A conditional update (e.g. `If-None-Match` /
  `If-Match` semantics offered by S3 implementations) would make multi-writer
  concurrency safe.

* *Streaming transactions.* The transaction interface buffers pending objects
  in memory uncompressed until commit. Large pushes can therefore consume a
  great deal of RAM. Streaming objects into the pack as they arrive would
  remove this limit.

* *Delta computation in repack.* Geometric repacking currently performs
  verbatim copies and therefore cannot exploit deltas or detect duplicate
  objects.

* *Bitmap support.* Some bitmap-using code paths currently encounter
  downcasts that the S3 ODB source cannot satisfy.  Operations affected by
  this can fall back to `pack.useBitmaps=false`; first-class bitmap support
  is a longer-term goal.

* *Content-addressable reftables.* Reftables are currently stored in
  `<gitdir>/reftables`. This should be changed eventually so that reftables are
  stored in the same `<commondir>/s3-cache` hierarchy as packfiles.
  Furthermore, reftables should be stored in a content-addressable way.
